# Atomic issues and PRs

## Contract

| Field | Bound contract |
|---|---|
| Trigger | User says "atomic PRs" or requests one issue or PR per logical change. |
| Authority | Remote: creates branches, commits, issues, and pull requests (GitHub) or merge requests (GitLab) on the selected forge; requires explicit human invocation. Preview the target repo/project and consequence before creating them. |
| Side effect | Creates branches, commits, issues, and PRs/MRs on the selected forge. Never force-pushes or pushes to protected branches without explicit user authorization. |
| Done | One issue or PR/MR per logical change on the correct base/head, links appended, URLs reported. |

## Inputs

Required: a working tree containing the change-set to publish and an authenticated forge account (`gh`-authenticated for GitHub, `glab`-authenticated for the GitLab host).
Select the forge from the verified request URL or repository remote; never assume a hardcoded public host. When the URL/remote does not clearly identify one forge, stop and ask; never guess GitHub.
Validate the repository selector before any repo-scoped call and pass the validated value to every call: GitHub `OWNER/REPO` must match `^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$`; GitLab `GROUP/PROJECT` must be a non-empty slash-separated path with no whitespace or control characters.
Optional: per-unit routing overrides (issue+PR/MR vs PR/MR-only) stated by the user; dependency order among units.
## Procedure

1. Authenticate to the selected forge. GitHub: run `gh auth status`; if unauthenticated, stop and ask the user to run `gh auth login`. GitLab: run `glab auth status --hostname <host>` with `<host>` taken from the verified remote (self-managed hosts included, never assumed `gitlab.com`); if unauthenticated, stop and ask the user to run `glab auth login --hostname <host>` with a token carrying `api` and `write_repository` scopes. Never set `GITLAB_TOKEN=$CI_JOB_TOKEN`: it is sent as `PRIVATE-TOKEN` and fails.
2. Resolve the canonical (upstream) target before any permission check. Read remotes with `git remote -v`; pick the contribution target as `upstream` if present, else `origin`. GitHub: detect a fork relationship with `gh repo view <slug> --json nameWithOwner,parent,defaultBranchRef`; a non-null `parent` means the canonical slug is `parent.nameWithOwner`. GitLab: detect a fork with `glab repo view <project> -F json` and read its fork-source relationship; a non-null fork source means the canonical project is the source path. If there is no clear single upstream (no `upstream` remote and ≥2 plausible non-origin candidates, or the detected fork source disagrees with the `upstream` remote) or `origin` has genuinely diverged from upstream (no common merge-base, or `origin` was re-created/renamed/renewed), prompt the user for the target repo/project. Plain fork-behind, where `origin` is merely behind `upstream` with a shared merge-base, is not ambiguity and must never prompt.
3. Query permission on the canonical target. GitHub: `gh repo view <canonical-slug> --json viewerPermission`; `viewerPermission` ∈ {ADMIN, MAINTAIN, WRITE} ⇒ direct mode; otherwise ⇒ fork mode. Record the canonical default base branch from `defaultBranchRef`. GitLab: read the access level from the same `glab repo view -F json` resource; `Developer` or higher on the canonical project ⇒ direct mode; otherwise ⇒ fork mode. Record the canonical default base branch from its `default_branch` field.
4. Group working-tree changes into atomic units by mechanism/file boundary: one concern per unit. Never bundle unrelated changes. Commit the whole set into N atomic commits first, running the repo-native type-checker and linter before each commit. Each unit becomes one self-contained commit, which allows per-unit branches to be created by cherry-picking. Never re-stage a dirty tree, which would let later units swallow earlier diffs. Present the unit→commit list to the user, then proceed.
5. Route each unit by whether it changes observable behavior: behavior-affecting → Issue + linked PR/MR, because a tracking issue gives the change a changelog/discussion anchor; mechanical → PR/MR-only, because a self-explanatory change needs no separate tracking. Honor an explicit per-unit override if the user states one; otherwise route silently.
6. Resolve the push URL once, by URL not remote name, to avoid undefined targets and remote-name collisions. GitHub direct mode: push URL = `https://github.com/<canonical-slug>`. GitHub fork mode: fork owner = `gh api user --jq .login`; fork slug = `<login>/<repo>`. If `origin` already points to a prior personal fork whose owner ≠ canonical owner and ≠ the authenticated login, print a non-blocking warning noting the account mismatch; do not stop the run. If the fork does not exist, create it with `gh repo fork <canonical-slug> --clone=false` and note the fork slug in the output. GitHub push URL = `https://github.com/<fork-slug>`. GitLab: build the push URL from the verified host, never hardcoded `gitlab.com`: direct mode `https://<host>/<canonical-project>`; fork mode `https://<host>/<fork-path>` after `glab repo fork <canonical-project> --clone=false` when the fork does not exist.
7. For each unit, in dependency order:
   1. Create the branch and cherry-pick the unit commit. Independent unit: `git branch <branch> <canonical-default-base>` then `git cherry-pick <unit-commit>`; PR/MR bases on `<default>`. Dependent unit in direct mode: parent-ref = the prerequisite unit's already-pushed branch; PR/MR bases on that branch (a stacked PR/MR); cherry-pick only this unit's commit so no prerequisite is lost. Dependent unit in fork mode: cross-fork stacking cannot be expressed (a GitHub fork PR's base must be a branch in the canonical repo; a GitLab MR targets one branch in one target project), so flatten onto `<canonical-default-base>` and prefix the body with a warning line naming the prerequisite unit and noting the dependency was flattened; the compromise is never silent.
   2. `git push <push-url> <branch>:refs/heads/<branch>` (same form both forges and modes; only the URL differs).
   3. GitHub: `gh pr create --repo <canonical-slug> --body-file <tmp>`. Direct mode: `--base <parent-ref> --head <branch>`; fork mode: `--base <default> --head <fork-owner>:<branch>`; capture PR `#M`. GitLab: `glab mr create --repo <canonical-project> --title "<summary>" --description-file <tmp> --source-branch <branch> --target-branch <parent-or-default> -y`, adding `--head <fork-path>` in fork mode; capture MR `!M` (project-scoped IID; address every MR by IID, never by global id). `--head` selects the head repository while the branch travels in `--source-branch`, unlike `gh --head <user>:<branch>`. `glab mr create` has no general dry run: run the exact previewed command only after the user approves the title, branches, and project.
   4. If the unit routed to Issue + linked PR/MR: GitHub `gh issue create --repo <canonical-slug> --title "<summary>" --body-file <tmp>` with a body that references PR `#M`; capture `#N`. GitLab: `glab issue create --repo <canonical-project> --title "<summary>" --description-file <tmp> -y` after approval, with a description that references MR `!M`; capture `#N` (project-scoped IID). Creation and update use body files and non-interactive flags (`-y`/`--yes`) only after exact user approval.
   5. Amend the body by appending `Closes #N` to the existing body, which closes the linked issue on merge on both forges. Reuse the body-file from step 3 (append the line and rewrite the file) or fetch the current body first: GitHub `gh pr view <M> --json body` then `gh pr edit <M> --repo <canonical-slug> --body-file <amended-tmp>`; GitLab: read the description from `glab mr view <iid> -F json` (whole-resource output; select the description locally) then `glab mr update <iid> --repo <canonical-project> --description-file <amended-tmp> -y` after approval. Body-file writes replace the whole body, so never write a bare `Closes #N` as the entirety of it.
   6. Emit the issue/PR/MR URLs; move to the next unit.
8. For PR/MR-only routed units (no issue filed in step 4), skip the issue-create and body-amend steps entirely; no dangling `Closes`. Done when: every logical unit has the correct issue/PR/MR routing, base and head, links, and reported URLs.

Record each unit's exact source snapshot, original parent boundary, intended delta, dependency, and resulting commit. For committed mixed input, reconstruct from committed blobs; for authorized working-tree input, preserve the full snapshot before extracting units. Do not confuse those two input modes.

For dependent dirty workspaces, preserve the base and feature snapshots first, construct the base unit, then transport only the feature delta measured from its recorded pre-integration boundary onto the resulting parent. A successful three-way application is not the postcondition: compare the reconstructed content and verify every intended repair remains. Prove each unit on its own committed tree and on the actual published parent before publication; union-green does not establish slice-green.

In direct stacking, publish a dependent unit against its already-published prerequisite. In fork-mode flattening, include the prerequisite content required for the unit to work and disclose the flattened dependency in the PR/MR body. Verify the remote base/head and complete compare range after creation. Existing human invocation, target preview, protected-branch, and no-force rules remain unchanged.

- Unauthenticated: stop before any mutation; ask the user to run `gh auth login` (GitHub) or `glab auth login --hostname <host>` (GitLab). No partial result.
- Ambiguous upstream: stop and ask the user for the target repo/project; do not guess. No mutation performed.
- Ambiguous forge: the URL/remote does not clearly identify GitHub or GitLab; stop and ask. Never guess GitHub. No mutation performed.
- Insufficient permission with no fork path: stop; report the canonical slug/project and the missing permission. No push or object created.
- Push rejected: report the rejection and the branch/URL; do not force-push. Leave prior successfully published units in place.
- Partial publish failure mid-loop: already-published units remain; report each unit's status (published URL or failed) so the user can retry the failed units. Never swallow the error or pretend the done predicate holds.
- Non-converged: if any unit could not be published, the terminal result names the failed units and the reason; the run is not done.

A run report listing, per unit: the routing (Issue+PR/MR or PR/MR-only), the branch, the push URL, the PR/MR number (IID on GitLab) and URL, and (when filed) the issue number and URL. Classify the run as done only when one issue or PR/MR per logical change exists on the correct base/head, links are appended, and URLs are reported.
