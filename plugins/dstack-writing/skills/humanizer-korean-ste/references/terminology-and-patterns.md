# 용어와 문장 패턴

모든 예시는 이 패키지를 위해 작성한 가상 사례이다. 실제 장비나 서비스의 동작 설명으로 사용하지 않는다.
이 파일은 기본 규칙을 보충한다. 특정 프로젝트의 확인된 정의가 있으면 그 정의를 우선한다.

## 용어 목록의 범위

이 목록은 문서에서 혼동하기 쉬운 개념과 반복되는 기술 용어를 관리하는 소규모 용어 목록이다.
영어 STE 사전의 한국어 번역본으로 표시하지 않는다. 공식 한국어 STE 사전으로 표시하지 않는다.
모든 한국어 단어를 열거하지 않는다. 목록 밖 단어를 일괄 금지하지 않는다.
아래 용어 결정은 문서 내 예제 결정 및 임시 결정이다. 준수 주장의 근거로 사용하지 않는다.

필요한 정보는 개념 식별자, 대표 용어, 정의, 범위, 근거와 상태이다.
한 문서의 임시 결정과 조직의 공식 승인을 구분한다.
기존 용어집과 충돌하면 새로운 표현을 자동 승인하지 않는다.

### 예제 용어 목록

아래 정의는 예제 문서 안에서 사용하는 정의이다. 실제 프로젝트에 자동 적용하지 않는다.

| 개념 식별자 | 대표 용어 | 정의 | 구분할 개념 | 상태 |
|---|---|---|---|---|
| identity-check | 인증 | 요청자가 제시한 신원을 확인하는 과정 | 자원 사용 권한의 판정 | 예제 정의 |
| permission-check | 인가 | 특정 자원을 사용할 권한이 있는지 판정하는 과정 | 신원 확인 | 예제 정의 |
| write-config | 설정 저장 | 편집한 설정을 설정 파일에 기록하는 작업 | 서버에 설정을 적용하는 작업 | 예제 정의 |
| apply-config | 설정 적용 | 저장된 설정을 서버의 동작에 반영하는 작업 | 설정 파일을 기록하는 작업 | 예제 정의 |

### 한국어 활용

대표 동사가 `저장하다`이면 `저장하십시오`, `저장하면`, `저장했습니다`를 문맥에 맞게 사용할 수 있다.
`저장됨`이라는 상태명과 `저장하다`라는 행동을 동일한 문장 역할로 취급하지 않는다.
명사화된 형태나 활용형을 탐지했다는 사실만으로 비승인 용어로 판정하지 않는다.

문서의 실제 UI 이름이 `Save changes`이면 해당 표기를 유지한다.
본문에서 작업 개념을 설명할 때는 확인된 한국어 대표 용어를 사용한다.
UI 문자열을 용어 통일의 대상으로 삼아 자동 번역하지 않는다.

### 신규 용어 처리

기존 용어와 뜻이 같으면 기존 대표 용어를 사용한다.
뜻이 다르면 별도 개념으로 기록한다. 뜻이 불분명하면 원문을 유지하고 확인한다.
조직의 승인 절차가 없으면 `문서 내 임시 용어`로만 사용할 수 있다.
임시 용어가 핵심 작업의 해석을 결정하는 경우 확정된 실행 절차로 제시하지 않는다.

## 행동과 설명의 분리

이 예제의 근거 정보:

`운영자는 설정 파일을 저장한 다음 서버를 다시 시작해야 한다.`
`서버는 시작할 때 저장된 설정 파일을 읽는다.`

### 작업 절차

작업자: 운영자.

1. 설정 파일을 저장하십시오.
2. 서버를 다시 시작하십시오.

### 동작 설명

서버는 시작할 때 저장된 설정 파일을 읽습니다.

동작 설명을 `설정 파일을 읽으십시오`라는 작업 지시로 변환하지 않는다.
서버 재시작과 설정 저장은 이 예제에서 별도 작업이다.
`설정을 반영하십시오`로 통합하면 실제로 수행할 행동이 불분명해진다.

## 조건의 범위

### 한 행동의 조건

원문: `검증에 실패하면 요청을 거부합니다.`

설명: `검증에 실패하면 시스템이 요청을 거부합니다.`

이 교정은 시스템이 주체라는 문맥이 확인된 경우에만 유효하다.
검증 성공 시의 동작은 원문에 없으므로 추가하지 않는다.

### 여러 행동에 적용되는 조건

원문: `승인을 받은 경우에만 A를 제출한 다음 B를 제출하십시오.`

교정:

`승인을 받은 경우에만 다음 두 단계를 수행하십시오.`

1. A를 제출하십시오.
2. B를 제출하십시오.

조건이 첫 단계에만 적용되는 것처럼 기술하지 않는다.
일회성 조건 확인을 지속적 감시로 확대하지 않는다. 지속 조건을 일회성 확인으로 축소하지 않는다.
승인 상태의 평가 시점이 작업에 중요하고 원문에 명시되지 않았다면 확인한다.

### 필요조건과 충분조건

`관리자일 때만 실행할 수 있습니다`는 관리자 권한이 필요조건이라는 뜻이다.
다른 조건의 충족 여부는 이 문장으로 판단할 수 없다.
`관리자이면 실행할 수 있습니다`로 변경하면 다른 조건의 존재 가능성이 소거될 수 있다.

### 조건 결합

둘 다 필요한 경우에는 `A와 B를 모두 충족하면`과 같이 기술한다.
하나 이상이면 되는 경우에는 `A 또는 B 중 하나 이상을 충족하면`과 같이 기술한다.
정확히 하나여야 하는 경우에는 `A와 B 중 하나만 충족하면`과 같이 기술한다.
원문이 `및/또는`으로 모호하면 위 세 가지 중 어느 뜻인지 근거 자료에서 확인한다.
근거가 없으면 의미를 추측하여 선택하지 않는다. 해당 단계를 확정하지 않고 확인을 요청한다.

## 순차 작업과 동시 작업

원문: `버튼을 누른 다음 레버를 당기십시오.`

교정:

1. 버튼을 누르십시오.
2. 레버를 당기십시오.

원문: `버튼을 누른 상태를 유지하면서 레버를 당기십시오.`

교정: `버튼을 누른 상태를 유지하면서 레버를 당기십시오.`

두 번째 문장을 두 단계로 기계적으로 분리하면 유지 상태가 소실된다.
단계 분리보다 작업 의미의 보존을 우선한다.

## 판정 기준이 없는 작업

원문: `온도가 충분히 낮아지면 덮개를 여십시오.`

대응: 덮개를 열 수 있는 온도 기준이 원문이나 관련 자료에 있는지 확인한다.
기준이 없으면 해당 작업의 확정을 보류한다.
`30°C 이하`와 같이 그럴듯한 값을 임의로 삽입하지 않는다.

원문: `실패하면 몇 차례 다시 시도하십시오.`

대응: 재시도의 위험, 간격, 상한이 실제 작업에 필요한지 확인한다.
정책이 필요한 문서라면 미확정 사항으로 보고한다.
`3회`, `5초 간격`, `지수 백오프`를 일반적 관행이라는 이유로 추가하지 않는다.

## 절차문에서 금지하는 세 가지 틀

한국어 출력과 이 패키지의 설명문에서 아래 세 가지 틀을 사용하지 않는다.
원문에 이 틀이 있으면 아래 교정 방식에 따라 수정한다.
아래 `원문` 예시는 금지 대상을 제시하기 위한 것이다. 출력에 옮기지 않는다.

### 상투적 대조 구문

금지 형태: `A가 아니라 B`, `단순한 A가 아닌 B`, `A라기보다는 B`, `A뿐만 아니라 B`.

배제할 행동이 있으면 수행할 행동을 먼저 기술한다. 금지 사항은 별도 단계나 별도 문장으로 기술한다.
대상의 성격은 그 대상이 무엇인지를 긍정문으로 서술한다.

원문: `설정 파일을 삭제하는 것이 아니라 보관하십시오.`

교정:

1. 설정 파일을 보관하십시오.
2. 설정 파일을 삭제하지 마십시오.

원문: `이 단계는 단순한 확인이 아닌 승인 절차입니다.`

교정: `이 단계는 승인 절차입니다.`

원문: `이 작업은 재시작이라기보다는 설정 다시 읽기입니다.`

교정: `이 작업은 설정 파일을 다시 읽습니다. 이 작업은 서버를 다시 시작하지 않습니다.`

원문: `로그뿐만 아니라 설정 파일도 백업하십시오.`

교정:

1. 로그를 백업하십시오.
2. 설정 파일을 백업하십시오.

### 사선 병기

금지 형태: `A/B`, `A / B`, `및/또는`, `을/를`, `통과 / 확인 필요 / 보류`.

본문과 템플릿에서 사선으로 두 항목을 병기하지 않는다. 항목 간 관계를 `와`, `및`, `또는`, `중 하나`로 명시하거나 항목을 분리하여 기술한다.
조사 템플릿에는 `을(를)`을 사용한다.
코드, `/srv/app/config.toml`과 같은 경로, URL, 단위, 날짜, UI 문자열 안의 사선은 보호 문자열이므로 유지한다.

원문: `설정을 저장/적용하십시오.`

교정:

1. 설정을 저장하십시오.
2. 설정을 적용하십시오.

원문 템플릿: `{대상}을/를 선택하십시오.`

교정 템플릿: `{대상}을(를) 선택하십시오.`

원문: `로그 및/또는 설정 파일을 백업하십시오.`

교정: 근거 자료에서 둘 다 필요한지, 하나 이상이면 되는지, 정확히 하나여야 하는지 확인한다.
둘 다 필요하다고 확인되면 `로그와 설정 파일을 모두 백업하십시오.`로 기술한다.
근거가 없으면 해당 단계를 확정하지 않고 확인을 요청한다.

원문 템플릿: `판정: 통과 / 확인 필요 / 보류`

교정 템플릿: `판정: {판정 값}`. 판정 값에는 `통과`, `확인 필요`, `보류` 중 하나를 기재한다.

### 양비론적 유보

금지 형태: `A일 수도 있고 B일 수도 있고 둘 다 아닐 수도 있습니다`, 결정 없이 끝나는 `상황에 따라 다릅니다`, 결정 없이 끝나는 `장단점이 있습니다`.

통제된 절차에서 이 틀은 실행을 차단하는 모호함이다. 해당 단계를 확정하지 않는다.
결정을 좌우하는 조건을 확인 사항으로 명시한다. 결정을 임의로 만들어 내지 않는다.

원문: `재시작은 무중단 방식일 수도 있고 전체 재시작일 수도 있습니다. 상황에 따라 다릅니다.`

교정: 실행용 본문에서 해당 단계를 확정하지 않는다. 검토 보고서에 다음과 같이 기록한다.

`문제: 재시작 방식을 정하는 조건이 원문에 없습니다.`

`처리: 결정 조건과 조건별 재시작 방식을 확인하기 전까지 해당 단계의 확정을 보류합니다.`

원문이 결정 조건을 제시하면 조건문으로 변환한다.

원문: `접속 중인 사용자가 있으면 무중단 재시작을 하고, 없으면 전체 재시작을 합니다. 장단점이 있습니다.`

교정:

1. 접속 중인 사용자가 있는지 확인하십시오.
2. 접속 중인 사용자가 있으면 무중단 재시작을 수행하십시오.
3. 접속 중인 사용자가 없으면 전체 재시작을 수행하십시오.

`장단점이 있습니다`와 같이 결정에 기여하지 않는 문장은 제거한다.

## 경고의 위치와 등급

다음은 제공된 예제 정책이 해당 경고를 요구한다고 가정한 사례이다.

원문:

`기존 설정 파일을 삭제하십시오.`

`주의: 설정 파일을 삭제하면 저장된 설정을 복구할 수 없습니다.`

교정:

`주의: 설정 파일을 삭제하면 저장된 설정을 복구할 수 없습니다.`

`기존 설정 파일을 삭제하십시오.`

경고를 해당 행동 앞으로 이동한다. 이 예제의 경고 내용을 모든 파일 삭제에 일반화하지 않는다.
`주의`를 `위험`으로 변경하지 않는다. 근거 없이 백업이나 전원 차단 같은 추가 작업을 지시하지 않는다.
고정 문구는 표현을 수정하지 않고 위치와 적용 범위만 검토한다.

## 실행용 문서와 검토 보고서

실행용 본문에는 확인되지 않은 값이나 빈 명령 인수를 넣지 않는다.
검토 보고서는 본문과 분리한다.

검토 예:

`위치: 3단계.`

`문제: 대기 종료 조건이 없습니다.`

`규칙: 실행조건구체화.`

`판정: 보류.`

`처리: 종료 조건을 확인하기 전까지 삭제 단계의 확정을 보류합니다.`

`판정` 항목에는 `통과`, `확인 필요`, `보류` 중 하나를 기재한다.
이 보고는 문서 검토 결과만 기록한다. 작업 수행이나 기술적 안전성 검증의 증거로 사용하지 않는다.
